# Design rationale

## Why this external server

The domain problem is a decision that changes with the weather: whether a
school can legally and physically operate on site. Sanitary regulations for
Ukrainian general secondary schools require at least 17 C in classrooms, hot
running water, and electricity for lighting and the canteen. Only the first of
these depends on outdoor conditions, and it is the one that fails first during
a cold spell combined with damaged infrastructure.

The OpenWeather MCP server therefore supplies the one input the local registry
cannot contain: what the next three days will be like. Its result is not
decoration. It determines the severity class, the severity class determines
every school status, and the statuses determine the plan and the generator
queue. Change the forecast and the same registry produces a different plan.

An alternative would have been Playwright against a public weather page. It
was rejected: scraping introduces markup fragility for data that is already
available through a designed contract.

## Why each custom tool exists at the MCP boundary

The boundary question is what the model must be able to choose between, and
what it must never compute itself.

`edu_classify_weather_severity` exists separately because the severity class
is the join between the two servers. It is the only tool that converts raw
meteorology into a domain concept, and its output is the input of the other
two. Folding it into planning would hide that link: the plan would depend on
the forecast through an invisible internal step, and it would be impossible to
show which forecast produced which class. Keeping it separate also allows the
severity class to be supplied by hand when the forecast is unavailable, which
is exactly what the degradation path does.

`edu_assess_school_readiness` exists because assessment and allocation answer
different questions. Assessment answers "can this school work on site, and
why"; it is useful on its own to an education department that has no
generators to distribute at all. It also returns the diagnostic fields
(`limiting_factor`, `gaps`) that explain a decision, which a plan alone would
not carry.

`edu_plan_learning_mode` exists because allocating a scarce resource is a
different operation from evaluating a state. It applies the filter, the
ranking, and the cut-off at the available count, and it reports what the
allocation could not cover (`unassigned_candidates`). That number is a
management fact, not a by-product.

None of the three is a retrieval tool. Each applies domain rules to a state
and returns a decision with its justification.

## How the tool set supports the workflow

    weather (external)
      -> get_forecast: text parsed into three daily records
      -> edu_classify_weather_severity: overall_severity
      -> edu_assess_school_readiness(severity)
      -> edu_plan_learning_mode(severity, generators_available)
      -> summary written by the model

The model decides which tool to call and in what order, and writes the final
explanation. It computes nothing. Every figure in the answer comes from a tool
result, and every school-level decision carries a `reason` or `rationale`
string generated by the deterministic code, so the explanation can be traced
back to the rule that produced it.

Parsing the forecast is deliberately done in agent code rather than by the
model. The external server returns roughly forty three-hour slots as plain
text; grouping them by date and taking a minimum is arithmetic, and arithmetic
performed by a language model is neither reliable nor reproducible. The model
receives three clean daily records instead of 5.7 KB of text.

## Trade-offs

**Thresholds are a decision, not a regulation.** No Ukrainian regulation
states an outdoor temperature at which schools must switch to distance
learning; the founding authority decides. The thresholds used here are
anchored at both ends: -20 C is the design winter temperature for Kyiv under
DSTU-N B V.1.1-27, and the upper anchor is the 17 C classroom requirement.
They live in a versioned config file, and `thresholds_version` appears in
every response, so a result can always be attributed to the rule set that
produced it.

**Heat and electricity are modelled separately.** They fail for different
reasons. Boiler houses commonly have their own generators, so heating can
survive a blackout. That does not make heating independent: a boiler house can
be damaged, and if it draws from a combined heat and power plant, that link is
vulnerable too. Electric heaters give only `partial` capability, because they
warm individual rooms rather than a building and stop entirely without power.

**Limiters differ in strength on purpose.** No power is an immediate `fail`:
without electricity there is no lighting and no canteen, so on-site teaching is
impossible regardless of temperature. No hot water caps the status at
`at_risk`: it is a regulatory gap requiring a decision by the founding
authority, not a physically unusable building. Partial power degrades the
status by one step rather than deciding it.

**One criterion per step in the allocation.** Candidates are filtered before
ranking, not after, so schools that a generator cannot help never compete for
one. Ranking uses `students_primary` alone, with `students_total` and
`school_id` only as tie-breakers. Making `students_total` a second scoring
criterion would require explaining how the two are weighed against each other;
a single criterion keeps the result deterministic and explainable.

**Two `at_risk` schools can get different modes.** A school that received a
generator is scheduled on site; a school with the same resulting status but no
intervention is not. The mode reflects not only the state but whether the
founding authority acted. Treating both as on-site with restrictions is a
defensible alternative; the conservative option was chosen.

## Known limitations

- The forecast carries no wind and no precipitation. Current wind is
  substituted for all days and snowfall is set to zero. Both substitutions are
  reported in the tool result and repeated in the answer, so no figure is
  presented as measured when it is assumed.
- `inspection_overdue` compares against today's date, which makes that single
  gap flag non-reproducible across time. It affects no status. Passing an
  evaluation date as a parameter would remove the dependency.
- The dataset contains no school with `power_level = none`, because every
  school with an `outage` status also has a generator. That branch of the
  logic is implemented and reachable but not exercised by the current data.
- Severity is derived from minimum temperature and two flags only. Duration of
  a cold spell, wind chill, and the thermal inertia of a building are not
  modelled.
- The agent holds no state between runs. Each invocation is independent, which
  is appropriate for a decision recomputed from current conditions.
